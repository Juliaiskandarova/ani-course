Ниже представлены четыре согласованные диаграммы PlantUML: вариантов использования, классов, последовательности подачи заявки и состояний брони.

Во всех диаграммах используются одинаковые названия сущностей **Клиент, Камера, Заявка, Бронь** и статусы брони **Подтверждена, Отменена**.

## **1. Диаграмма вариантов использования (Use Case)**

Показывает границу системы, внешних акторов и доступные им действия. Условия подтверждения, отказа и отмены приведены в примечаниях.

```

@startuml
title Диаграмма вариантов использования

left to right direction
skinparam packageStyle rectangle

actor "Клиент" as Client
actor "Сотрудник проката" as Employee

rectangle "Система проката камер" {

  usecase "Подать заявку" as UC1
  usecase "Просмотреть свои брони" as UC2
  usecase "Отменить свою\nподтвержденную бронь" as UC3
  usecase "Просмотреть все брони" as UC4

}

Client --> UC1
Client --> UC2
Client --> UC3

Employee --> UC4

note bottom of UC1
  Заявка содержит:
  - камеру;
  - начало интервала;
  - конец интервала.

  Начало должно быть раньше конца.

  Если существует пересекающаяся
  подтвержденная бронь той же камеры:
  отказ с причиной, бронь не создается.

  Иначе, при корректном интервале:
  создается бронь со статусом
  "Подтверждена".
end note

note bottom of UC3
  Отмена допустима, только если:
  - бронь принадлежит клиенту;
  - статус брони = "Подтверждена".

  После отмены:
  статус = "Отменена".
  Запись сохраняется.
end note

note bottom of UC4
  Сотрудник видит все брони,
  включая отмененные.
end note

@enduml

```

## **2. Диаграмма классов (Class Diagram)**

Отражает атрибуты сущностей, кратности связей и ограничения на интервалы. Заявка моделируется как входные данные, а не как сохраняемая бронь.

```

@startuml
title Диаграмма классов

skinparam classAttributeIconSize 0

class "Клиент" as Client {
  +ФИО: String
  +почта: String
}

class "Камера" as Camera {
  +серийныйНомер: String
  +модель: String
}

class "Заявка" as Request <<входные данные>> {
  +начало: DateTime
  +конец: DateTime
}

class "Бронь" as Booking {
  +начало: DateTime
  +конец: DateTime
  +статус: СтатусБрони
}

enum "СтатусБрони" as BookingStatus {
  Подтверждена
  Отменена
}

Client "1" -- "0..*" Request : подает
Camera "1" -- "0..*" Request : указывается в

Client "1" -- "0..*" Booking : имеет
Camera "1" -- "0..*" Booking : относится к

note right of Request
  Корректный интервал:
  начало < конец.

  Заявка не является бронью.

  При отказе объект "Бронь"
  не создается.
end note

note right of Booking
  Новая бронь создается
  со статусом "Подтверждена"
  только при отсутствии конфликта.

  Пересечение интервалов A и B:
  A.начало < B.конец
  AND
  B.начало < A.конец

  Конфликт учитывается только
  для броней той же камеры
  со статусом "Подтверждена".

  Статус "Отменена":
  запись сохраняется,
  интервал не блокируется.
end note

note bottom of BookingStatus
  Других статусов брони нет.

  Отказ в заявке не является
  статусом брони.
end note

@enduml

```

**Проверка кратностей:**

| Связь           | Со стороны первой сущности  | Со стороны второй                      |
| --------------- | --------------------------- | -------------------------------------- |
| Клиент — Бронь  | Один клиент на бронь (`1`)  | 0 или более броней у клиента (`0..*`)  |
| Камера — Бронь  | Одна камера на бронь (`1`)  | 0 или более броней у камеры (`0..*`)   |
| Клиент — Заявка | Один клиент на заявку (`1`) | 0 или более заявок у клиента (`0..*`)  |
| Камера — Заявка | Одна камера на заявку (`1`) | 0 или более заявок для камеры (`0..*`) |

Кратности указаны непосредственно на обоих концах каждой ассоциации в PlantUML.

## **3. Диаграмма последовательности подачи заявки (Sequence Diagram)**

Здесь показаны проверка интервала, поиск конфликтов и обе ветки результата: **отказ без создания брони** и **создание подтвержденной брони**.

```

@startuml
title Последовательность подачи заявки

autonumber

actor "Клиент" as Client

box "Система проката камер"
  participant "Обработка заявок" as System
  database "Брони" as Store
end box

Client -> System : Подать заявку(камера, начало, конец)
activate System

alt начало >= конец

  System --> Client : Ошибка: некорректный интервал

else начало < конец

  System -> Store : Найти брони той же камеры\nсо статусом "Подтверждена",\nпересекающие интервал
  activate Store

  note right of Store
    Пересечение существует, если:

    бронь.начало < заявка.конец
    AND
    заявка.начало < бронь.конец

    Статус "Отменена"
    не учитывается.
  end note

  Store --> System : Результат поиска
  deactivate Store

  alt Найдена пересекающаяся подтвержденная бронь

    System --> Client : Отказ с причиной:\nинтервал занят

    note right of System
      Объект "Бронь" НЕ создается.
      Сохранения новой брони нет.
    end note

  else Пересечений нет

    System -> Store : Создать бронь(клиент, камера,\nначало, конец,\nстатус = "Подтверждена")
    activate Store

    Store --> System : Созданная бронь
    deactivate Store

    System --> Client : Подтверждение брони

  end

end

deactivate System

@enduml

```

Проверка случаев пересечения для соседних и перекрывающихся интервалов:

Существующая подтвержденная бронь: 10:00–12:00

Соприкосновение границ 09:00–10:00 или 12:00–14:00 разрешено; пересечение 11:00–13:00 вызывает отказ.

## **4. Диаграмма состояний брони (State Diagram)**

Показывает только состояния **существующей брони**. Отказ не является состоянием, потому что при отказе объект брони не создается.

```

@startuml
title Диаграмма состояний брони

hide empty description

state "Подтверждена" as Confirmed
state "Отменена" as Cancelled

[*] --> Confirmed : Создание брони\n[начало < конец\nи нет пересекающейся\nподтвержденной брони\nтой же камеры]

Confirmed --> Cancelled : Отменить\n[инициатор = клиент брони]

note top of Confirmed
  Бронь существует и блокирует
  указанный интервал камеры.

  Отказ в заявке не порождает
  объект "Бронь".

  Поэтому перехода
  в состояние "Отказана" нет.
end note

note right of Cancelled
  Запись брони сохраняется.

  Интервал больше не блокируется.

  Обратный переход
  не предусмотрен требованиями.
end note

@enduml

```

Важные особенности: при отмене не происходит удаления объекта, а отказ в заявке не приводит к появлению объекта в диаграмме состояний. У отмененной брони не показаны дальнейшие переходы, поскольку они не определены требованиями.

## **5. Допущения и принятые обозначения**

1. **Заявка** представлена временным набором входных данных. Требования не предусматривают отдельное постоянное хранение заявок, поэтому оно не моделируется.
2. **Некорректный интервал** в диаграмме последовательности приводит к сообщению об ошибке без создания брони. R7 определяет корректность интервала, но конкретный способ сообщения об ошибке не задан. Это единственное дополнительное допущение о реакции системы.
3. **Обработка заявок** и **Брони** на диаграмме последовательности — условные внутренние компоненты системы, а не дополнительные внешние акторы или бизнес-правила.
4. Интервалы трактуются как `[начало, конец)`. Это техническое представление правила R7, при котором соседние интервалы могут соприкасаться.
5. Никакие дополнительные роли, статусы, правила оплаты, сроки отмены или ограничения на количество броней не вводятся.

## **6. Матрица соответствия R1–R8**

| Требование | Конкретные элементы диаграмм                                                                                                                                       |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **R1**     | Use Case: «Подать заявку». Class: `Заявка`, `начало`, `конец`, связь с `Камерой`. Sequence: первое сообщение клиента.                                              |
| **R2**     | Sequence: поиск пересекающихся подтвержденных броней и ветви `alt` — отказ с причиной или создание. State: переход в `Подтверждена` только при выполнении условий. |
| **R3**     | Use Case: «Просмотреть свои брони», «Отменить свою подтвержденную бронь». State: переход `Подтверждена → Отменена` с проверкой владельца.                          |
| **R4**     | Use Case: внешний актор «Сотрудник проката» и действие «Просмотреть все брони».                                                                                    |
| **R5**     | Class: `Камера` с `серийныйНомер`, `модель`; `Клиент` с `ФИО`, `почта`.                                                                                            |
| **R6**     | Class: ассоциации `Клиент "1" -- "0..*" Бронь` и `Камера "1" -- "0..*" Бронь`.                                                                                     |
| **R7**     | Class: `начало < конец`, формула пересечения. Sequence: проверка корректности, строгое сравнение границ.                                                           |
| **R8**     | State: состояние `Отменена` с примечанием о сохранении записи. Sequence: проверяются только брони со статусом `Подтверждена`.                                      |

## **7. Итоговая проверка согласованности**

**Отказ из-за пересечения**

Бронь не создается; операция сохранения отсутствует в ветке отказа.

**Некорректный интервал**

Бронь не создается; реакция системы выделена в допущениях.

**Успешная заявка**

Создается бронь со статусом «Подтверждена».

**Отмена**

Только владелец может отменить подтвержденную бронь; статус становится «Отменена».

**Сохранение истории**

Отмененная бронь остается в системе и больше не блокирует интервал.

**Соседние интервалы**

Разрешены благодаря строгому сравнению границ.

**Названия и статусы**

Одинаковы во всех четырех диаграммах.

**Результат:** все восемь требований отражены. Главное ограничение соблюдено: **отказанная заявка не создает бронь**, а отмена существующей брони не удаляет запись. Неопределенное поведение при некорректном интервале явно вынесено в допущения.
