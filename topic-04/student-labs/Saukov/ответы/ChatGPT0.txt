Ниже представлены **4 диаграммы UML** по требованиям R1–R8. Каждая диаграмма оформлена как отдельный, полный и готовый к использованию блок PlantUML.

## **1. Диаграмма вариантов использования (Use Case)**

Отражает действия клиента и сотрудника проката, а также проверки при подаче заявки.

```

@startuml
left to right direction
skinparam packageStyle rectangle
skinparam shadowing false

actor "Клиент" as Client
actor "Сотрудник проката" as Employee

rectangle "Система бронирования камер" {

    usecase "Подать заявку\nна бронирование" as UC1
    usecase "Проверить\nкорректность интервала" as UC2
    usecase "Проверить\nдоступность камеры" as UC3
    usecase "Создать\nподтвержденную бронь" as UC4
    usecase "Отказать в заявке\nс указанием причины" as UC5

    usecase "Просмотреть\nсвои брони" as UC6
    usecase "Отменить свою\nподтвержденную бронь" as UC7

    usecase "Просмотреть\nвсе брони" as UC8
}

Client --> UC1
Client --> UC6
Client --> UC7

Employee --> UC8

UC1 ..> UC2 : <<include>>
UC1 ..> UC3 : <<include>>

UC4 ..> UC1 : <<extend>>
UC5 ..> UC1 : <<extend>>

note right of UC2
  Начало интервала < конца
end note

note right of UC3
  Пересечения проверяются только
  с подтвержденными бронями
  той же камеры.
  Соседние интервалы допустимы.
end note

note bottom of UC4
  Условие:
  интервал корректен
  и пересечений нет
end note

note bottom of UC5
  Условие:
  некорректный интервал
  или найдено пересечение
end note

note bottom of UC7
  Отменять можно только
  свою подтвержденную бронь.
  Запись сохраняется.
end note

@enduml

```

## **2. Диаграмма классов (Class Diagram)**

Описывает сущности, их атрибуты, связи, кратности и операции системы.

```

@startuml
skinparam classAttributeIconSize 0
skinparam shadowing false
top to bottom direction

class "Клиент" as Client {
    - id: Integer
    - фио: String
    - email: String
}

class "Камера" as Camera {
    - id: Integer
    - серийныйНомер: String
    - модель: String
}

class "Бронь" as Booking {
    - id: Integer
    - начало: DateTime
    - конец: DateTime
    - статус: СтатусБрони
    --
    + отменить(): void
}

enum "СтатусБрони" as BookingStatus {
    ПОДТВЕРЖДЕНА
    ОТМЕНЕНА
}

class "СотрудникПроката" as Employee {
    - id: Integer
}

class "СервисБронирования" as Service {
    + податьЗаявку(
        клиент: Клиент,
        камера: Камера,
        начало: DateTime,
        конец: DateTime
      ): РезультатЗаявки

    + проверитьИнтервал(
        начало: DateTime,
        конец: DateTime
      ): Boolean

    + естьПересечение(
        камера: Камера,
        начало: DateTime,
        конец: DateTime
      ): Boolean

    + получитьБрониКлиента(
        клиент: Клиент
      ): List<Бронь>

    + отменитьБронь(
        клиент: Клиент,
        idБрони: Integer
      ): Boolean

    + получитьВсеБрони(): List<Бронь>
}

class "РезультатЗаявки" as Result {
    + успешно: Boolean
    + бронь: Бронь [0..1]
    + причинаОтказа: String [0..1]
}

Client "1" -- "0..*" Booking : оформляет
Camera "1" -- "0..*" Booking : бронируется

Booking --> BookingStatus : статус

Client ..> Service : использует
Employee ..> Service : использует

Service ..> Client
Service ..> Camera
Service ..> Booking
Service ..> Result

note right of Booking
  начало < конец

  Отмененная бронь
  сохраняется в системе.

  Каждая бронь имеет
  ровно одного клиента
  и одну камеру.
end note

note bottom of Service
  Пересечение для интервалов
  [a1, a2) и [b1, b2):

  a1 < b2 AND b1 < a2

  Проверяются только брони
  со статусом ПОДТВЕРЖДЕНА.

  Соседние интервалы
  не пересекаются.

  Отменять бронь может
  только ее клиент.
end note

note bottom of Result
  При успехе:
  успешно = true,
  бронь заполнена.

  При отказе:
  успешно = false,
  причинаОтказа заполнена,
  новая бронь не создается.
end note

@enduml

```

## **3. Диаграмма последовательности подачи заявки (Sequence Diagram)**

Показывает полный процесс обработки заявки: проверку интервала, поиск пересечений, отказ или создание подтвержденной брони.

```

@startuml
autonumber
skinparam shadowing false

actor "Клиент" as Client
boundary "Интерфейс системы" as UI
control "Сервис бронирования" as Service
database "Хранилище броней" as DB

Client -> UI : Выбрать камеру,\nначало и конец интервала
activate UI

Client -> UI : Подать заявку

UI -> Service : податьЗаявку(\nклиент, камера, начало, конец)
activate Service

Service -> Service : проверитьИнтервал(начало, конец)

alt Начало >= конца
    Service --> UI : Отказ:\n"Некорректный интервал"
    UI --> Client : Показать причину отказа

else Начало < конца

    group Атомарная проверка и создание брони

        Service -> DB : Найти подтвержденные брони\nдля выбранной камеры
        activate DB

        DB --> Service : Список подтвержденных броней
        deactivate DB

        Service -> Service : Проверить пересечение:\nначало < бронь.конец AND\nбронь.начало < конец

        alt Найдено пересечение
            Service --> UI : Отказ:\n"Камера занята в выбранный интервал"
            UI --> Client : Показать причину отказа

        else Пересечений нет
            create participant "Новая бронь" as Booking

            Service -> Booking : Создать бронь(\nклиент, камера, начало, конец)

            Service -> Booking : Установить статус\nПОДТВЕРЖДЕНА

            Service -> DB : Сохранить бронь
            activate DB

            DB --> Service : Бронь сохранена
            deactivate DB

            Service --> UI : Успех: подтвержденная бронь
            UI --> Client : Показать подтверждение
        end
    end
end

deactivate Service
deactivate UI

note over Service, DB
  Проверка пересечений и сохранение
  должны выполняться атомарно,
  чтобы параллельные заявки
  не создали конфликтующие брони.

  Отказ не создает запись о брони.
end note

@enduml

```

## **4. Диаграмма состояний брони (State Diagram)**

Отображает жизненный цикл брони. Согласно требованиям, у созданной брони только два возможных состояния: подтверждена и отменена.

```

@startuml
skinparam shadowing false

state "Подтверждена" as Confirmed
state "Отменена" as Cancelled

[*] --> Confirmed : Заявка принята\n[интервал корректен\nи пересечений нет]

Confirmed : entry / Сохранить бронь
Confirmed : do / Блокировать интервал камеры

Confirmed --> Cancelled : Клиент отменяет свою бронь

Cancelled : entry / Изменить статус на ОТМЕНЕНА
Cancelled : do / Не блокировать интервал

note right of Confirmed
  Бронь принадлежит
  одному клиенту
  и одной камере.

  Интервал камеры
  считается занятым.
end note

note right of Cancelled
  Запись о брони
  остается в системе.

  Интервал освобождается
  для новых бронирований.

  Повторная отмена
  не допускается.
end note

note bottom of Confirmed
  Если интервал некорректен
  или пересекается с уже
  подтвержденной бронью,
  заявка отклоняется.

  Объект брони при отказе
  не создается, поэтому
  состояние "Отклонена"
  отсутствует.
end note

@enduml

```

## **Соответствие диаграмм требованиям**

| Требование                                                | Где отражено                     |
| --------------------------------------------------------- | -------------------------------- |
| R1 — Подача заявки с камерой и интервалом                 | Use Case, Class, Sequence        |
| R2 — Проверка пересечений, отказ или подтверждение        | Use Case, Class, Sequence, State |
| R3 — Просмотр и отмена своих броней                       | Use Case, Class, State           |
| R4 — Просмотр всех броней сотрудником                     | Use Case, Class                  |
| R5 — Атрибуты камеры и клиента                            | Class                            |
| R6 — Связи с кратностями 1 и 0..\*                        | Class                            |
| R7 — Корректность и соприкосновение интервалов            | Use Case, Class, Sequence        |
| R8 — Сохранение отмененной брони и освобождение интервала | Class, State                     |

**Важные решения модели:**

- **Отказ в заявке не является состоянием брони:** при отказе бронь вообще не создается.
- **Отмененная бронь не удаляется:** изменяется только ее статус, а запись остается доступной для просмотра.
- **Интервалы рассматриваются как полуоткрытые&#x20;**`[начало, конец)`**:** например, бронь 10:00–12:00 не конфликтует с бронью 12:00–14:00.
- **Пересечения проверяются только между подтвержденными бронями одной камеры.**
