Ниже — четыре диаграммы в нотации PlantUML. Имена сущностей, статусы и формулировки согласованы между ними: заявка (`Request`), бронь (`Booking`), статусы `Подтверждена` / `Отменена`.

## Допущения

- Авторизация и идентификация клиента/сотрудника вне рамок модели (не следуют из R1–R8).
- «Пересечение интервалов» — стандартное: `началоA < конецB и конецA > началоB` (строгие неравенства — тогда соприкасающиеся интервалы не пересекаются, это R7).
- При отказе заявка считается обработанной, но запись брони не создаётся.
- Редактирование брони не предусмотрено правилами, поэтому в диаграмме состояний его нет.

## 1. Диаграмма вариантов использования

```plantuml
@startuml
left to right direction
skinparam packageStyle rectangle

actor "Клиент" as Client
actor "Сотрудник проката" as Staff

rectangle "Система проката камер" {
  usecase "Подать заявку\n(камера, начало, конец)" as UC1
  usecase "Проверить пересечение\nс подтверждёнными бронями" as UC2
  usecase "Создать подтверждённую бронь" as UC3
  usecase "Отказать с причиной" as UC4
  usecase "Просмотреть свои брони" as UC5
  usecase "Отменить свою\nподтверждённую бронь" as UC6
  usecase "Просмотреть все брони" as UC7
}

Client --> UC1
Client --> UC5
Client --> UC6
Staff --> UC7

UC1 ..> UC2 : <<include>>
UC2 ..> UC3 : <<extend>>\n[нет пересечения]
UC2 ..> UC4 : <<extend>>\n[есть пересечение]

note bottom of UC3
  R2: бронь создаётся сразу в статусе «Подтверждена»
end note

note bottom of UC6
  R3: клиент может отменить только свою
      бронь в статусе «Подтверждена»
end note
@enduml
```

## 2. Диаграмма классов

```plantuml
@startuml
skinparam classAttributeIconSize 0

class Client {
  fullName : String
  email : String
}

class Camera {
  serialNumber : String
  model : String
}

class Booking {
  intervalStart : DateTime
  intervalEnd : DateTime
  status : BookingStatus
}

enum BookingStatus {
  CONFIRMED
  CANCELLED
}

Client "1" -- "0..*" Booking : имеет >
Camera "1" -- "0..*" Booking : относится к >

Booking ..> BookingStatus

note bottom of Booking
  R7: инвариант intervalStart < intervalEnd
  R2: создать Booking со статусом CONFIRMED можно
      только если нет пересечения с бронями той же
      камеры в статусе CONFIRMED
  R8: переход в CANCELLED не удаляет запись;
      CANCELLED-бронь исключается из проверки пересечений
end note

note bottom of Camera
  R6: бронь относится ровно к одной камере
      и одному клиенту
end note
@enduml
```

## 3. Диаграмма последовательности — подача заявки

```plantuml
@startuml
actor "Клиент" as Client
participant "Система проката камер" as System

Client -> System : подать заявку(камера, начало, конец)
activate System
System -> System : проверка: начало < конец (R7)
System -> System : поиск пересечений с подтверждёнными\nбронями той же камеры (R2)

alt найдено пересечение
  System --> Client : отказ, причина = бронь №N\n(интервал уже занят)
  note right
    R2: ветка отказа.
    Объект Booking НЕ создаётся —
    заявка обработана, брони нет.
  end note
else пересечений нет
  System -> System : создать Booking(камера, клиент,\nинтервал, статус = Подтверждена)
  System --> Client : подтверждение, бронь №N
end note
deactivate System
@enduml
```

## 4. Диаграмма состояний брони

```plantuml
@startuml
[*] --> Подтверждена : заявка принята,\nпересечений нет (R2)

Подтверждена : блокирует интервал камеры
Подтверждена : видна клиенту (свои) и сотруднику (все)

Подтверждена --> Отменена : отмена клиентом (R3)

Отменена : запись сохраняется (R8)
Отменена : интервал не блокирует (R8)
Отменена : не участвует в проверке пересечений

note bottom of Подтверждена
  Ветка отказа из R2 не входит в жизненный цикл брони:
  при отказе заявки объект Booking не создаётся вовсе.
end note
@enduml
```

## Сопоставление R1–R8 с элементами диаграмм

| Правило | Где отражено |
|---|---|
| **R1** | В UC1: параметры варианта использования «Подать заявку (камера, начало, конец)»; в последовательности — сообщение `подать заявку(камера, начало, конец)` |
| **R2** | В UC2–UC4: `include` проверки и два `extend`-варианта; в последовательности — блок `alt` (отказ с причиной / создание брони со статусом Подтверждена); в классах — примечание у `Booking` о создании только без пересечений |
| **R3** | В UC5 и UC6 (с примечанием об отмене только своей подтверждённой брони); в последовательности и состояниях — переход `Подтверждена → Отменена` по отмене клиентом |
| **R4** | В UC7 «Просмотреть все брони» для актора «Сотрудник проката» |
| **R5** | В классах: атрибуты `Camera.serialNumber`, `Camera.model`, `Client.fullName`, `Client.email` |
| **R6** | В классах: кратности `Client 1 — 0..* Booking` и `Camera 1 — 0..* Booking` (одна бронь — ровно к одной паре «камера+клиент», у каждой — много броней) |
| **R7** | В последовательности — проверка `начало < конец` до ветвления; в классах — инвариант `intervalStart < intervalEnd`; в допущениях — строгие неравенства при проверке пересечения, что разрешает соприкасающиеся интервалы |
| **R8** | В состояниях: статус `Отменена` с пометками «запись сохраняется» и «не блокирует интервал»; в классах — примечание, что `CANCELLED` исключается из проверки пересечений |

Ключевая проверка «отказ ≠ бронь» реализована в трёх местах: ветка `alt … отказ` в последовательности не содержит вызова создания объекта, вариант использования «Отказать с причиной» не связан с UC3 «Создать подтверждённую бронь», а примечание в диаграмме состояний прямо выводит отказ за пределы жизненного цикла брони.

Если нужно, могу перевести диаграммы на английские идентификаторы (для кода) или дополнить диаграммой последовательности для отмены брони.
