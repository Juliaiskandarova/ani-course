# Диаграммы для системы бронирования камер

Ниже — четыре диаграммы PlantUML. Имена сущностей, акторов и статусов сквозные: `Клиент`, `СотрудникПроката`, `Заявка`, `Бронь`, `Камера`, статусы `ПОДТВЕРЖДЕНА` / `ОТМЕНЕНА` / `ОТКАЗАНА`.

## 1. Диаграмма вариантов использования

```plantuml
@startuml UC
left to right direction
skinparam packageStyle rectangle

actor "Клиент" as Client
actor "Сотрудник проката" as Staff

rectangle "Система бронирования камер" {
  usecase "Подать заявку\n(камера, начало, конец)" as UC_Apply
  usecase "Получить отказ с причиной\n(пересечение с подтвержденной бронью)" as UC_Reject
  usecase "Создать подтвержденную бронь" as UC_Confirm
  usecase "Проверить корректность интервала\n(начало < конец)" as UC_Validate
  usecase "Проверить пересечение\nс подтвержденными бронями" as UC_CheckOverlap
  usecase "Просмотреть свои брони" as UC_ViewOwn
  usecase "Отменить свою\nподтвержденную бронь" as UC_Cancel
  usecase "Просмотреть все брони" as UC_ViewAll
}

Client --> UC_Apply
Client --> UC_ViewOwn
Client --> UC_Cancel

Staff --> UC_ViewAll

UC_Apply ..> UC_Validate : <<include>>
UC_Apply ..> UC_CheckOverlap : <<include>>
UC_CheckOverlap <.. UC_Reject : <<extend>>\n[пересечение найдено]
UC_CheckOverlap <.. UC_Confirm : <<extend>>\n[пересечения нет]

note right of UC_Cancel
  Условие: бронь принадлежит
  клиенту и имеет статус
  ПОДТВЕРЖДЕНА.
  Отмена сохраняет запись (R8).
end note

note bottom of UC_Confirm
  При отказе бронь НЕ создается (R2).
end note
@enduml
```

## 2. Диаграмма классов

```plantuml
@startuml Class
skinparam classAttributeIconSize 0

class Клиент {
  - фИО : String
  - почта : String
  + податьЗаявку(камера, начало, конец)
  + просмотретьСвоиБрони()
  + отменитьБронь(бронь)
}

class СотрудникПроката {
  - фИО : String
  + просмотретьВсеБрони()
}

class Камера {
  - серийныйНомер : String
  - модель : String
}

class Заявка {
  - камера : Камера
  - начало : DateTime
  - конец : DateTime
  - результат : {ПОДТВЕРЖДЕНА, ОТКАЗАНА}
  - причинаОтказа : String
}

class Бронь {
  - начало : DateTime
  - конец : DateTime
  - статус : {ПОДТВЕРЖДЕНА, ОТМЕНЕНА}
}

Клиент "1" -- "0..*" Заявка : подает >
Клиент "1" -- "0..*" Бронь : владеет >
Камера "1" -- "0..*" Заявка : указывается в >
Камера "1" -- "0..*" Бронь : относится к >
Заявка "0..1" --> "0..1" Бронь : порождает\n[только при ПОДТВЕРЖДЕНА]

note right of Заявка
  R2: при пересечении с подтвержденной
  бронью результат = ОТКАЗАНА,
  бронь не создается (связь 0..1).
end note

note bottom of Бронь
  R8: ОТМЕНЕНА сохраняется,
  не блокирует интервал.
  R7: начало < конец; соседние
  интервалы могут соприкасаться
  (конецA <= началоB).
end note
@enduml
```

## 3. Диаграмма последовательности подачи заявки

```plantuml
@startuml Seq
actor "Клиент" as Client
participant "Система бронирования" as Sys
participant "Хранилище броней" as Store

Client -> Sys : податьЗаявку(камера, начало, конец)
Sys -> Sys : проверить интервал\n[начало < конец]
alt интервал некорректен
  Sys --> Client : отказ (некорректный интервал)
else интервал корректен
  Sys -> Store : найти подтвержденные брони\nэтой камеры, пересекающие интервал
  Store --> Sys : список броней
  alt найдено пересечение (R2)
    Sys --> Client : отказ с причиной\n(пересечение с подтвержденной бронью)
    note right of Sys : бронь НЕ создается
  else пересечения нет (R7: касание допустимо)
    Sys -> Store : создать бронь\nстатус = ПОДТВЕРЖДЕНА
    Store --> Sys : бронь сохранена
    Sys --> Client : бронь подтверждена
  end
end
@enduml
```

## 4. Диаграмма состояний брони

```plantuml
@startuml State
[*] --> ПОДТВЕРЖДЕНА : заявка принята\n(пересечения нет)
[*] --> ОТКАЗАНА : заявка отклонена\n(пересечение найдено)\nбронь не создается

state ПОДТВЕРЖДЕНА {
  ПОДТВЕРЖДЕНА : блокирует интервал
}
state ОТМЕНЕНА {
  ОТМЕНЕНА : запись сохраняется\nинтервал не блокируется
}
state ОТКАЗАНА {
  ОТКАЗАНА : запись заявки с причиной\nбронь отсутствует
}

ПОДТВЕРЖДЕНА --> ОТМЕНЕНА : отмена клиентом\n[бронь принадлежит клиенту]
ОТМЕНЕНА --> [*]
ОТКАЗАНА --> [*]
@enduml
```

## Сопоставление требований R1–R8 с элементами диаграмм

- **R1** — UC `Подать заявку (камера, начало, конец)`; класс `Заявка` с полями `камера, начало, конец`; сообщение `податьЗаявку(камера, начало, конец)` на диаграмме последовательности.
- **R2** — UC `Проверить пересечение с подтвержденными бронями` + ветки `<<extend>>` «пересечение найдено» (отказ с причиной) / «пересечения нет» (подтверждение); на sequence — `alt найдено пересечение` → отказ, бронь не создается; на классах связь `Заявка --> Бронь` кратности `0..1` (при отказе брони нет); на состояниях переход `[*] --> ОТКАЗАНА` с пометкой «бронь не создается».
- **R3** — UC `Просмотреть свои брони`, `Отменить свою подтвержденную бронь`; методы `Клиент.просмотретьСвоиБрони()`, `Клиент.отменитьБронь()`; переход `ПОДТВЕРЖДЕНА --> ОТМЕНЕНА` с условием `[бронь принадлежит клиенту]`.
- **R4** — актор `СотрудникПроката`, UC `Просмотреть все брони`, метод `просмотретьВсеБрони()`.
- **R5** — атрибуты `Камера.серийныйНомер`, `Камера.модель`, `Клиент.фИО`, `Клиент.почта`.
- **R6** — ассоциации с кратностями на обоих концах: `Клиент "1" -- "0..*" Бронь`, `Камера "1" -- "0..*" Бронь` (одна бронь — одна камера и один клиент; у каждого — много броней).
- **R7** — UC `Проверить корректность интервала`; примечание к `Бронь` «начало < конец; соседние интервалы могут соприкасаться (конецA <= началоB)»; на sequence — ветка `[начало < конец]` и пометка «касание допустимо».
- **R8** — состояние `ОТМЕНЕНА` (запись сохраняется, интервал не блокируется) и примечание к UC `Отменить…`; на sequence проверка пересечения учитывает только статус `ПОДТВЕРЖДЕНА`.

## Допущения

1. «Пересечение» интервалов трактуется стандартно: `началоA < конецB И началоB < конецA`; касание (`конецA == началоB`) пересечением не считается — это прямо следует из R7.
2. Отказ при некорректном интервале (R7) оформлен как отдельная ветка sequence-диаграммы; R2 про пересечение применяется только к корректным интервалам. Новых правил не вводится — это уточнение порядка проверок.
3. При отказе сохраняется запись `Заявка` с результатом `ОТКАЗАНА` и причиной (это отражено только для заявки; требование R8 о сохранении касается отмененной брони и здесь не расширяется).
4. Сотрудник проката в рамках R1–R8 только просматривает брони; прав на создание/отмену ему не добавлено.
